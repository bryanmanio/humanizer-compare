# Copy compare

Run humanizer over a site's copy, then show the result as a side-by-side before/after view the user can scroll through. Every run produces the same three things:

1. The copy edits, made in the source files.
2. A comparison view at `http://localhost:<port>/_compare/`: the before and after pages side by side with synced scrolling, changed text outlined (red before, green after), and a viewport picker (1280 / 1440 / 390). Hovering a green box shows the humanizer pattern and why the text changed. Keep the view minimal: no side panels or extra chrome.
3. A reply in the format under "Report back".

Paths below are relative to this skill's directory.

## 1. Load humanizer

Always read `humanizer/humanizer.md` in full before touching any copy. It's a pinned copy of https://github.com/blader/humanizer (see `humanizer/SOURCE`). Follow its rules exactly, especially:

- Don't add a fact, number, name or claim the source doesn't already make. If a clearer sentence would need one, write a simpler sentence instead. Re-check every edit for this before finishing, since it's the easiest rule to break.
- Patterns §1–§5 justify an edit on a single sighting. Patterns marked *weak alone* need other tells nearby.
- A pattern only counts when the text actually uses it. Copy that's already clean stays as it is, and saying so is a valid result.

## 2. Find the copy

"All my copy" means everything a visitor reads or hears:

- Headings, body text, buttons, link text, and the short and long variants of responsive text (for example, text swapped in at mobile widths).
- `<title>`, meta and Open Graph descriptions, `aria-label`, `alt`, and `title` attributes.
- Text inside generated figures or components, edited at its source. If a file says it's generated (`<!-- generated by X; edit there -->`), edit X and re-run the generator.
- Link-preview sources such as an `og.html`, if they repeat page copy.

Skip code, comments, and READMEs unless the user asks for them. Leave text that mocks real app UI (notifications, tooltips, menu rows) unchanged unless the user says the app's strings are changing too, and list it under "left alone". To list the copy quickly in a static page, strip `<svg>`, `<style>` and `<script>` blocks and read what's left.

## 3. Snapshot "before", then start the server

Take the snapshot **before editing anything**, or the "before" side will show new copy. Find the directory the dev server serves at `/` (the repo root for a plain static site, `public/` for most frameworks). Then, for each page:

```sh
# Static HTML served as-is (its own scripts keep working):
python3 -I <skill>/scripts/snapshot.py --serve-root <root> --page / --from-file index.html

# Rendered sites (Next, Astro, React, ...): save the rendered HTML first
#   SSR/SSG:      curl -s http://localhost:3000/pricing > /tmp/before-pricing.html
#   client-only:  save document.documentElement.outerHTML from a browser tab
python3 -I <skill>/scripts/snapshot.py --serve-root public --page /pricing \
  --from-html /tmp/before-pricing.html --strip-scripts
```

`--strip-scripts` stops hydration from re-rendering the snapshot with the new copy. The script prints the snapshot's URL path for `changes.json`, copies the viewer to `<root>/_compare/index.html`, and adds `_compare/` to `.git/info/exclude`, so the repo itself is untouched.

The viewer reads into both iframes, so **the before snapshot, the after page and the viewer must share an origin**: one server, one port. Use the project's own dev server if it has one, or `python3 -m http.server <port>` from the serve root, run in the background. Check that the port is free first.

## 4. Edit the copy

Apply the edits in place, matching surrounding formatting (line wrapping, entities like `&nbsp;`, quote style). Keep a list as you go: where each edit is, the before text, the after text, the humanizer pattern it fixes, and why. That list becomes `changes.json`.

## 5. Write `_compare/changes.json`

```json
{
  "pages": [
    {
      "name": "Home",
      "before": "/_compare/before/index.html",
      "after": "/",
      "changes": [
        { "where": "Privacy headline", "before": "Nothing leaves your Mac.", "after": "It talks to your server and nothing else.",
          "pattern": "§20 Decorative headings",
          "why": "A slogan written for effect, and not literally true: the app does talk to your server. The heading now states what it does." },
        { "where": "<title>", "before": "Ballast — your server…", "after": "Ballast: your server…",
          "pattern": "§8 Dashes as the universal connector",
          "why": "A dash skips deciding how the two halves relate. A colon says the second half explains the first.", "visible": false }
      ]
    }
  ],
  "settleMs": 600
}
```

- `after` must be text that actually appears on the page (at least its first 40 characters). The viewer matches it to a green box to attach the hover reason.
- `pattern` is the humanizer section number and title, exactly as written in `humanizer/humanizer.md` (for example "§12 Overused AI words"). For an edit that comes from a general rule rather than a numbered pattern, name the rule (for example "Every sentence must add something").
- `why` is one or two sentences that apply that pattern's **Problem** paragraph to this specific edit: what the old text did wrong and what the new text does instead. Quote the old wording where that helps. Don't paste the generic Problem text.
- Set `"visible": false` for titles, meta, and `aria-label`/`alt` changes. Their reasons show when hovering the change count in the header.
- Raise `settleMs` if the page plays an intro animation that changes text after it loads.

## 6. Verify the view

Open `http://localhost:<port>/_compare/` in a browser tab with whatever browser tool you have (Playwright, a Chrome DevTools MCP, or similar), and check that:

- The header shows a change count with no error message.
- Every green box has a reason: in the after frame, `document.querySelectorAll('.cmp-diff:not([data-why])')` returns nothing. If one is missing, fix that change's `after` text in `changes.json`.
- Hovering a green box shows the tooltip, and scrolling one side scrolls the other.
- The 390 viewport shows any mobile-only text that changed.

Take a screenshot of one changed section to confirm the highlights render. If you have no browser tool, give the user the URL and ask them to check it. Also look for layout knock-on effects, such as a headline that now wraps to an extra line, and report them.

## Report back

Use this format, kept short:

1. **Compare view:** the URL in a code span, plus one line on what's where: before on the left, after on the right, red and green highlights, hover a green box for the reason, sync scroll, viewport picker.
2. **What changed**, as a table with the columns *Where | Before | After | Pattern*, one row per edit.
3. **Left alone on purpose**: copy that already read well, mocked UI strings, anything skipped. Also any claim you considered adding and dropped because it wasn't in the source.
4. **Design knock-on effects** you noticed, such as wrapping or length changes.
5. **State of the repo:** nothing committed, `_compare/` is excluded from git, delete it when done, and the server is still running.

Don't commit unless the user asks.
